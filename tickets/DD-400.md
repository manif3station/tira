# DD-400: Make Dashboard Reads Scale With Records

## Method

Problem-solving performance TDD + filesystem-scan BDD.

## Expected happy path

- Dashboard output remains byte-for-byte equivalent in structure and ordering.
- Each selected board is scanned once, regardless of its number of columns.
- A representative multi-column dashboard completes materially faster than
  release 0.11 while preserving all records and configured columns.

## Problem statement and reproduction

`dashboard` currently calls `record_list` separately for every visible column.
Each call recursively scans and decodes every JSON record on that board before
discarding records from other columns. Benchmark an installed 0.11 disposable
project with many ticket columns and records using `tira.dashboard --type
ticket -o json`; record elapsed time, output counts, and ordering before and
after the fix.

## Problem-solving evidence

Installed 0.11 took 4.87, 4.99, and 4.72 seconds to render 240 tickets
distributed across 13 visible columns. The output contained all 240 records in
the configured order. The root cause was one recursive `record_list` scan and
JSON decode pass per column.

The first synthetic guard used only one visible column and could not
distinguish the algorithms; the corrected three-column guard failed with three
scans versus one expected. The fix calls `record_list` once per selected board
and groups its sorted records into configured columns in memory.

The identical benchmark then took 0.53, 0.78, and 0.45 seconds. Its JSON was
byte-for-byte identical to the pre-fix output, including all 240 records and
the same 13-column order: approximately 6x to 11x faster in these runs.

# DD-450

## Title

Tilde in answers, and line editing at every prompt.

## Method

CLI ATDD, red-first (`t/43-line-editing.t`), driven through a real
pseudo-terminal so the terminal handling is proven rather than excluded.

## Problem

Owner report: answering the directory question with `~/foo/bar` created
a directory literally named `~`, because a shell expands a tilde only in
an unquoted command-line argument — never in text typed at a prompt, and
never inside quotes. He also asked for Ctrl-A and Ctrl-E at any prompt,
which plain terminal input does not provide: canonical mode offers
backspace and nothing else.

## Design

- A leading `~` or `~/` is expanded wherever a path is accepted: the
  directory answer, and the `--dir` and `--project` flags, so a quoted
  `--dir "~/x"` behaves like an unquoted one instead of creating a
  strange directory. `$ENV{HOME}` is untainted on the way through, since
  the result becomes a filesystem path under the taint gate.
- Line editing is written directly against POSIX termios, which is core.
  The obvious alternative — `Term::ReadLine` — was measured first: no
  editing implementation (`::Gnu`, `::Perl`) is installed on the host or
  in the test image, so depending on one would have silently given the
  owner nothing at all.
- Supported: Ctrl-A and Ctrl-E as asked, plus Ctrl-U, Ctrl-K, backspace,
  left/right arrows, Home/End, and insertion at the cursor. Ctrl-C and
  Ctrl-D abandon the prompt, matching the existing end-of-input
  behaviour so the wizard's guarantees are unchanged.
- The editor engages only when input is a terminal; anything else — a
  pipe, a script, the test suite — takes the original plain read, so
  behaviour for automation is untouched.
- **Coverage without exclusions.** Terminal code is normally what gets
  waived; instead `IO::Tty` is added as a *test-only* dependency and the
  tests drive a real pseudo-terminal, so raw mode, every key, and the
  restore path all execute for real. No production dependency is added
  and the shipped skill is unchanged.

## Acceptance

- `~/foo/bar` typed at the directory prompt creates the project under
  the user's home; `--dir "~/x"` and `--project "~/x"` behave likewise;
  a path with no leading tilde is untouched
- at a terminal: Ctrl-A, Ctrl-E, Ctrl-U, Ctrl-K, backspace, arrows,
  Home/End, and mid-line insertion all behave; Ctrl-C and Ctrl-D abandon
- away from a terminal the prompt reads exactly as before
- Docker tests pass; coverage `100.0%` on all three modules with no
  exclusion; taint and primitive-scan gates pass; `cover_db` cleaned
- `SKILLS.md`, `docs/`, `Changes`, `VERSION 0.59`, tickets, BACKLOG,
  commit, and push complete

## Found while testing

Two defects the pty-driven tests exposed, neither of which the earlier
suite could have caught:

1. Pressing enter past the people question failed with "Every member
   needs a name". The empty-string guard exists for an explicit
   `--members ""` on a command line; at a prompt, enter means "none".
   The summary line then also assumed the answer was always present.
2. The first harness let the terminal driver pre-process the keystrokes,
   so DEL and Ctrl-U were handled by the tty in canonical mode rather
   than by the editor - a broken editor would have passed. The harness
   now puts the terminal in raw mode before sending anything, which is
   what made the real behaviour observable.

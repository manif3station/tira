# DD-407

## Title

Jira-parity attachment experience in the card dialog: inline viewing, upload,
per-comment attachments, and reference-safe deletion.

## Method

Engine/CLI TDD + HTTP ATDD + Browser BDD (Playwright), preceded by recorded
Jira research (this plan).

## Research: what the Jira issue dialog does with attachments

From the Atlassian issue-view design guidelines, Jira Cloud issue tickets
(JRACLOUD-81747, JRACLOUD-73397, JRACLOUD-72208), and community docs:

- The issue dialog has an Attachments section in strip (thumbnail) or list
  form; clicking an attachment opens an inline preview overlay — no download
  round trip — for images, PDF, and text-like files, with a download action
  inside the overlay for everything else.
- Files can be added from the dialog itself and deleted per attachment.
- Comments carry their own attached files; an attachment added while writing
  a comment belongs to that comment's context, distinct from the issue-level
  attachment strip.

## Problem

Tira's DD-406 dialog renders attachments as inert text rows. There is no way
to view an attachment without the CLI (`tira.attachment.get` to a file, then
open it by hand — exactly the download-and-open dance the dialog should
remove), no way to add or delete attachments from the browser, and comment
attachments are not visibly distinct or manageable.

## Design

### Engine

- `attachment_add_content( ref, filename, content, comment? )` — a
  content-based twin of `attachment_add` sharing the same sha-dedup and
  reference logic, so browser uploads need no temp file. `attachment_add`
  becomes a thin path-reading wrapper around it.
- `attachment_detach( ref, sha, extension?, comment? )` — removes the
  reference entry from the record (or from the named comment), then checks
  every record in the project: if no reference to that sha+extension
  remains anywhere, the stored file is physically removed through the
  existing logged `attachment_remove`; otherwise the file stays for the
  other referents. Dies clearly when the reference does not exist. This
  keeps `attachment_remove` as the sole physical deletion path and makes
  browser deletion safe under sha dedup.
- CLI parity: `tira.attachment.detach --ref REF --sha SHA [--extension EXT]
  [--comment ID] [-o FORMAT]`, documented in `SKILLS.md` (still exactly 100
  use cases; an existing attachment use case is refined, none added).

### Routes (browser providers, shared builder)

- `GET /attachment?ref=REF&sha=SHA&extension=EXT` — streams the bytes with a
  Content-Type chosen by extension: images (`png jpg jpeg gif webp svg`) as
  their image type, `pdf` as `application/pdf`, text-like
  (`txt md log csv json yml yaml xml html`) as `text/plain; charset=UTF-8`
  (plain text deliberately, so HTML never executes in the viewer frame),
  everything else as `application/octet-stream` with an attachment
  disposition carrying the original filename. Unknown sha answers 404.
- `POST /attachment/add` — JSON `{ref, filename, content_base64, comment?}`,
  decoded and size-capped (16 MB) before `attachment_add_content`; returns
  the stored reference with the dedup flag, 422 on failure.
- `POST /attachment/remove` — JSON `{ref, sha, extension?, comment?}` →
  `attachment_detach`; 422 on failure.

### Dialog UI

- The Attachments section becomes a chip strip: filename + extension badge,
  a View control, and a Delete control per chip, plus an Add file picker.
- View opens an in-dialog overlay: `<img>` for images, `<iframe>` for PDF
  and text (src = the `/attachment` URL), and for other types a download
  link — one click to see, no manual download/save/open.
- Delete asks for confirmation, posts `/attachment/remove`, and re-reads the
  record.
- Add reads the picked file with FileReader, posts base64, and re-reads.
- Every comment renders its own attachment chips (same viewer) and its own
  Attach control posting with the comment id, so comment attachments stay
  visually and structurally owned by the comment.
- All new markup keeps the DD-406 visual language and ASCII-safe escapes.

## Acceptance

- clicking an image, PDF, or text attachment opens the inline overlay viewer
  fed by `/attachment` with the correct Content-Type, and closes without
  leaving the dialog; other types offer a named download instead
- HTML content is served as plain text in the viewer (no script execution)
- the dialog adds a record-level attachment via base64 upload, shows the
  dedup-aware stored name, and re-renders with the new chip
- the dialog deletes an attachment: the reference leaves the record; the
  stored file is physically removed only when no other record or comment
  still references it (proven by a dedup-shared fixture), and the deletion
  is logged
- each comment shows its own attachments and can attach a file owned by
  that comment through `comment` id, never mixed into the record strip
- `attachment_add_content`, `attachment_detach`, and
  `tira.attachment.detach` are covered by engine and CLI tests, including
  unknown-reference and oversized-upload failures
- routes decode strict UTF-8 filenames (`£`, CJK) and answer failures as
  structured 422 JSON; `/attachment` 404s on unknown sha
- Docker tests pass; coverage stays `100.0%` statement and subroutine;
  taint/perlsec and entrypoint gates pass; `cover_db` cleaned
- Playwright proves: viewer overlay opens with the right frame src for an
  image and a text file, upload posts the right payload, delete posts the
  right payload and respects confirmation, and a comment-owned attachment
  renders inside its comment
- `README.md`, `docs/`, `SKILLS.md`, `Changes`, `VERSION 0.18`, tickets,
  commit, and push complete from the `tira` repository

# DD-442

## Title

Optional Cpanel::JSON::XS acceleration for every read path.

## Method

Measurement-led design discussion, then engine TDD (`t/38-json-backend.t`)
with the existing 1,365-test suite as the regression net.

## Problem

The owner proposed a card-folder storage tier, partly to avoid parsing
JSON when only a title is needed. Measurement on a board built to match
his (138 records, 32.7KB average, 20 comments and 5 gate entries each)
showed where the time actually goes:

| path | before |
| --- | --- |
| dashboard, refs only | 2 ms |
| dashboard with titles | 2076 ms |
| full export | 2070 ms |
| `search --field title` | 2234 ms |

Isolating the cost: reading all 138 files without parsing takes 2 ms;
JSON::PP decodes them in 1992 ms; an XS backend does it in 6 ms. The
bottleneck was never JSON or the file layout — it was the pure-Perl
parser, which the project had been using because JSON::PP is core and no
JSON dependency was ever declared.

## Design

- `_select_json_backend` walks a candidate list (`Cpanel::JSON::XS`,
  then `JSON::PP`) with `require`, returning the first that loads;
  `json_backend`, `json_object`, and `json_decode` expose it. No string
  eval, so the taint gate is unaffected.
- Every construction and decode in the three modules routes through
  those accessors. Boolean *values* stay `JSON::PP::true/false`: both
  backends share `JSON::PP::Boolean`.
- Safety case, proven rather than assumed: canonical, pretty, and
  non-reference encodings are byte-identical between backends, so
  stored records never rewrite on upgrade and `content_hash` never
  drifts. t/38 asserts this against whichever backend is installed, so
  a future divergent release fails the suite on that machine instead of
  silently changing hashes.
- `cpanfile` gains `recommends` rather than `requires`: the accelerator
  is compiled, and a hard dependency would put XS compilation in the
  macOS and Windows platform gate for a pure speed win.

## Loop record (regression the suite caught)

The existing migration tests failed once the XS backend was active:
JSON::PP silently tolerates `encode` on a bare scalar, while
Cpanel::JSON::XS enforces the specification and dies. Two sites
depended on that tolerance — the import diff comparison and the
`replace` deep clone, both of which encode arbitrary *field values*
including plain strings. Rather than patch the two failures found, the
sweep covered every value-bearing path: those two, plus `-o json`,
`-o json-pretty`, and the human JSON block, now state
`allow_nonref` explicitly, so output can never become stricter than it
was. Structural paths (records, envelopes, cache entries) stay strict
on purpose.

## Result

| path | before | after |
| --- | --- | --- |
| dashboard with titles | 2076 ms | 12 ms |
| full export | 2070 ms | 19 ms |
| export `--fields ref,title,column` | 2884 ms | 20 ms |
| `search --field title` | 2234 ms | 17 ms |

## Acceptance

- backend selection is ordered and falls back to JSON::PP; byte
  identity holds for canonical, pretty, and non-reference encodings;
  booleans, numbers, and non-ASCII survive decoding; a stored record is
  byte-for-byte what the reference encoder writes; content hashes match
  the reference computation
- Docker tests pass; coverage `100.0%`; taint gate passes; `cover_db`
  and fixtures cleaned; Playwright ×3 green
- `README.md`, `cpanfile`, `Changes`, `VERSION 0.52`, tickets, BACKLOG,
  commit, and push complete

## Status

Done. Agreed follow-ups from the same discussion: per-field history
next, then the card-folder tier reconsidered on its own merits.

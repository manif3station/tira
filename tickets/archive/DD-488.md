# DD-488

## Title

A dashboard that picks up a new Tira by itself.

## Source

Owner: he keeps up to ten browser dashboards open. Updating Tira means
visiting all ten and restarting each one, which is a chore that scales
with how useful the tool is.

## Why a page reload alone is not enough

The obvious answer — have the page reload itself — does not work. The
server process has the old `Tira.pm` in memory, so a reload is served
by the old code and produces the same old page. Both halves have to
move: the process must be running the new code, and the page must
fetch it.

## Design

- The rendered page carries the version it was built by. The `/data`
  payload carries the version the **running process** has in memory.
- On each `/data` request the server compares its in-memory version
  with the one installed on disk. If they differ, it **re-executes
  itself**: same process, same arguments, same port, new code.
- The in-flight request dies with it. That is deliberate and harmless:
  the page's refresh already tolerates a failed poll, and the next one
  lands on the new server.
- The page reloads only when it sees a version **different from its
  own**, which by then is a version the server is really serving. No
  race, at the cost of one skipped refresh cycle.

`exec` replaces the process rather than spawning one, so nothing is
forked and no shell is involved. The engine's no-external-process
guarantee is about the library; this is the long-running server command
restarting itself, and it goes through a seam a test can observe rather
than being called directly.

## Acceptance criteria

1. `/data` reports the version the running process has.
2. The page carries the version it was rendered by.
3. A version change on disk makes the server re-execute, with the same
   arguments it started with.
4. An unchanged version never does.
5. The page reloads when the served version differs from its own, and
   not otherwise.
6. A `.env` that cannot be read is treated as no change, rather than
   restarting in a loop.

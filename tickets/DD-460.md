# DD-460

## Title

Notification history in SQLite, so escalation counts itself.

## Epic

EPIC-457 — stale-card reminders.

## Owner decision this implements

Settled point 11: the escalation count lives in a `notification.db`
beside `project.yml`, one row per notification holding the card
reference, the column and the time, indexed on reference and column.
The level is `SELECT COUNT(*)` for that reference in its current
column, so **a move resets escalation for free** — rows written after a
move carry a different column name and the count starts again at one.
The owner chose this over writing a count onto the card, which also
removes the question of notifications polluting the card's hash, stamp
and history: the card is never rewritten at all.

Settled point 12: SQLite becomes a real dependency, and when it is
missing Tira says plainly that SQLite needs installing rather than
dying on a missing module. This is the first thing in Tira that is not
the filesystem; the owner accepted that knowingly.

## Design

- `notification_record` inserts one row per delivered notification and
  returns the level of the row it just wrote. Several references can be
  recorded in one call, in one transaction, because the collector sends
  one message covering many cards and either records them all or none.
- `notification_level` and `notification_list` **never create the
  database**. A project that has never notified reports level 0 and an
  empty list without a file appearing, so asking costs nothing and
  leaves nothing behind.
- `tira.stale --stale --with-level` decorates each stale card with its
  current level, so the collector builds its whole message from a
  single call rather than one query per card.
- The reference is validated as non-empty and nothing more. Deliberate:
  a card can be deleted between the scan and the send, and refusing to
  record that would lose the history of a message that really was
  delivered. Recording a row for a since-deleted card is harmless.

## Acceptance criteria

1. A project with no history reports level 0 for any card and creates
   no database file by being asked.
2. Recording returns 1, then 2, then 3 for the same card in the same
   column.
3. The same card in a different column starts again at 1.
4. Recording several references in one call writes one row each.
5. A failed insert inside a batch leaves no rows behind.
6. `notification_list` returns reference, column and time in order, and
   filters by reference.
7. `stale --stale --with-level` reports each card's level.
8. With SQLite unavailable, the error names SQLite and how to install
   it, and does not mention a Perl module failing to load.
9. CLI `notify.record` and `notify.list` with exit 2 on bad input.

# DD-492

## Title

Every command tells you what the thing you just touched still owes.

## Source

Owner, message 3213, generalising `DD-491` into a rule: reminders are
not a question feature. His example — create a ticket with nothing but
a title, no details, no acceptance criteria, no BDD, no checklist, and
Tira should say so. "每一樣東西都是好像一個 Reminder, 一個 Response":
every response carries them. And each must show an example command, not
merely describe what is missing, "because otherwise they will not know
how to do it".

He was explicit that this is a rule rather than a feature, and that the
examples he gave are a start rather than the whole list.

## The rule

For any command whose result is a thing an agent works on, the response
carries what that thing still visibly owes, each with the exact command
that settles it, filled in with the reference in question.

Three properties that make it work rather than become noise:

1. **Silent when nothing is owed.** A reminder that always appears is
   furniture and is read as furniture.
2. **Derived, never stored.** Worked out from the thing's own state, so
   it cannot disagree with the facts.
3. **Every reminder carries a runnable example.** Naming a gap without
   naming the remedy just moves the work.

## Scope for this ticket

Records — the case he gave. A ticket with no description, no acceptance
criteria, no test steps, no checklist, no assignee. Which of those are
worth mentioning is a judgement to make deliberately: a reminder for
every empty field would bury the two that matter, so the ones chosen
should be the ones whose absence actually blocks somebody later.

Questions already have this (`DD-491`, shipped in `0.95`): missing
reason, missing choices, missing or stale recording.

## Open question for the owner

Which fields on a record are worth a reminder? My instinct is
description, acceptance criteria and checklist — the three whose
absence makes a ticket unworkable by somebody who did not write it —
and to leave the optional metadata alone. Worth his answer before
building, since a badly chosen list is worse than none.

# DD-443

## Title

Per-field history: an append-only journal per record with windowed reads.

## Method

Engine TDD + CLI ATDD, red-first (`t/39-history.t`).

## Problem

Owner design discussion (Telegram, 2026-08-07): he wants the history of
each field — what changed, when, from what to what. His sketch made each
card a git repository. Measurement and review moved that to a native
journal: shelling out to `git` on every save would break two documented
properties (Tira invokes no shell or external process; every entrypoint
passes taint mode) and would make writes 10–50× slower to serve reads.
Agreed order in that discussion: JSON accelerator first (DD-442, shipped
in 0.52), per-field history next, card-folder storage reconsidered later.

## Design

- **One choke point, not twenty commands.** Every record write in the
  engine funnels through `_write_json` (multi-record transactions
  delegate to it), so journaling happens there: read the previous
  version of the record, diff it field by field against the new one, and
  append an entry per changed field. No per-command instrumentation, so
  no command can be added later that silently escapes history.
- **Storage:** `.tira/history/<REF>.jsonl`, append-only JSON Lines, one
  entry per field change. It sits outside the board directories, so
  record scans, `content_hash`, and every existing read are untouched —
  history can never change a hash or slow a board read.
- **Creation** records one entry per set field with `before: null` and
  `op: "create"`, so a field's timeline starts at its birth value rather
  than appearing from nowhere on first edit.
- **Moves** rename the file rather than rewriting it, so `record_move`
  journals the `column` change explicitly with `op: "move"`.
- **Attribution:** commands that already carry an author (comments,
  gates, evidence) record it; `record.update` and `record.move` gain an
  optional `--author`, validated as a known project person. Entries
  without an author are recorded honestly as unattributed rather than
  guessing.
- **Ordering vs durability:** the record is written atomically first and
  the journal appended after, both under the project lock. A failed
  append loses an entry but can never invent one — history that claims a
  change which did not happen is worse than history with a gap.
- **Reads:** `history_list` reuses the CA20 window semantics —
  `--last N` / `--first N`, `--field`, `--since`, `--where`, `--count` —
  and the CA09 truncation, so a 12KB description edit does not have to
  arrive whole.
- Git stays out of the hot path. A `tira.history.export` that
  materialises a real repository from the journal remains available as a
  later ticket if the owner wants git tooling.

## Acceptance

- every field change through any command appears in the journal with
  before, after, timestamp, and op; creation seeds per-field entries;
  moves record the column change
- journaling never alters the record, its `content_hash`, or any
  existing read path
- `history.list` supports field filtering, windows, since, count,
  truncation, and exits 2 on unknown fields
- author recorded when supplied and validated; unattributed changes are
  explicit
- Docker tests pass; coverage `100.0%`; taint and primitive-scan gates
  pass; `cover_db` cleaned
- `SKILLS.md` (signature, contract, use case within the fixed 100),
  `docs/`, `Changes`, `VERSION 0.53`, tickets, BACKLOG, commit, and push
  complete

## Result

Shipped in `0.53`. While building it, the single-choke-point design
surfaced a pre-existing gap worth its own ticket: the `_replace_record`
family (comments, checklists, gates, evidence, attachment references)
writes without taking the project lock, contradicting the documented
guarantee that every mutation locks. History still commits correctly for
those commands — they flush their own entries when no lock frame is
active — but the locking gap itself is raised as DD-444 rather than
silently widened into this ticket.

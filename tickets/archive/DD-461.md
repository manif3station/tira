# DD-461

## Title

A collector that fails has somebody to tell.

## Epic

EPIC-457 — stale-card reminders.

## Owner decision this implements

Settled points 19 to 22, from message 3048. A collector runs
unattended: when delivery fails there is nobody in the room to see it,
so the failure would pass silently and the owner would believe cards
were being chased when they were not.

- A mid-flight failure retries once; if the retry fails too, a warning
  is written rather than the failure passing silently.
- The warning is stored and **appended at the bottom of whatever any
  Tira command prints**, after the table or the list, where the next
  coding agent or human to run a command will see it.
- **Identical warnings are not repeated.** The same failure happening
  again leaves the existing warning standing rather than adding a
  second copy.
- The warning **says how to remove it**, so whoever fixes the cause can
  clear it and an agent reading it knows the message is actionable.
- It keeps appearing until it is cleared.

## Design

- Warnings live in `.tira/warnings.json` beside the project file, not
  in the notification database. Every command must be able to show them,
  and requiring SQLite for every command — including on a machine that
  has never notified anything — would be the wrong trade.
- The banner goes to standard output for human output and to standard
  error for every machine format. Deliberate, and a deviation worth
  stating: the owner asked for it at the bottom of what is printed, but
  appending text inside a JSON or TOON payload would corrupt it for the
  agent that is parsing it. Standard error is still read by both a human
  at a terminal and a coding agent capturing a command, so the warning
  is seen either way without breaking the payload.
- `warning.*` commands do not print the banner themselves, since
  listing warnings already shows them.
- The banner names the identifier and the exact command that clears it.

## Acceptance criteria

1. A warning survives, and appears under the output of an unrelated
   command, until it is cleared.
2. The same message added twice leaves one warning, keeping the first.
3. A different message adds a second.
4. The banner names each warning's identifier and how to clear it.
5. Human output carries the banner on standard output; machine formats
   keep the payload parseable and carry it on standard error.
6. Clearing by identifier removes only that one; clearing all empties.
7. Clearing an unknown identifier is refused and changes nothing.
8. A project with no warnings prints nothing extra and reads no file.
9. `warning.*` commands do not print the banner over their own output.

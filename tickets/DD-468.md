## Root cause

`lib/Tira.pm` has no `use utf8`, so Perl reads the source as bytes: a
literal `≡` in the file becomes three separate characters. The output
path then encodes those characters to UTF-8 again, so three characters
become six bytes and the browser shows the double-encoded mess he
photographed.

The rest of the renderer already knew this — the card dialog writes
`"—"` rather than an em dash for exactly this reason. I wrote the
editor's four icons as literal characters and did not follow the
convention that was already there.

## Fix

The four icons are written as JavaScript escapes: `≡` for the
grip, `◉` and `○` for a watched and unwatched eye, `×`
for remove.

## The guard that should have existed

Every embedded script and stylesheet is now asserted to be pure ASCII,
in **both** the static and the live rendering. That is the real
protection: it catches any literal glyph anywhere in the renderer, not
just these four.

My first attempt at the guard checked only the static rendering — where
the editor script does not exist at all — so it passed against the
broken build. Verified properly afterwards by putting a literal glyph
back: the guard fails on it.

## Acceptance criteria

1. The four icons reach the browser as the characters intended.
2. No embedded script or stylesheet contains a byte above ASCII, in
   either rendering.
3. The guard fails when a literal glyph is reintroduced.

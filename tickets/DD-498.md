# DD-498

## Title

The self-restart killed the dashboard it was meant to save.

## Source

Owner, from real use, upgrading 1.00 to 1.01 under a running board:

    d2 tira.dashboard -o browser
    --- after install 1.01
    { "error" : "Cannot resolve project selector ''" }
    --- then process exited

## Root cause, and why my test missed it

`DD-488` restarted by re-executing `$0`. When the board is launched
through the dashboard dispatcher, **`$0` is the dispatcher, not the
Tira entrypoint** — so the restart re-ran the wrong program with
arguments that meant nothing to it, and the board died.

My test called `Tira::CLI->run` directly, where `$0` *is* the test
file, so the assumption held and the test passed. It was testing the
mechanism under conditions the mechanism never meets in the field.

Second contributor: the board was started without `--project`, so the
project came from the environment. The restarted process was left to
rediscover it and could not.

## Fix

- The entrypoint is **derived from the command**, from the module's own
  location, rather than taken from `$0`. A typed command comes back as
  the same typed board.
- The target is **checked before anything is replaced**. If it cannot
  be found, the board carries on running slightly old code, because a
  restart that cannot work is worse than a stale board: it turns
  "running old code" into "not running".
- The project is **passed explicitly**, so the new process does not
  depend on a working directory or an environment variable that may not
  survive however it was launched.

## The lesson worth keeping

A test that exercises a mechanism under conditions it never meets in
production proves the mechanism, not the feature. The reproduction here
sets `$0` to a dispatcher path deliberately, because that is the state
that actually broke.

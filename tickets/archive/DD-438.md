# DD-438

## Title

Dialog live refresh repaints only what changed; editors survive
in-flight refreshes.

## Method

Browser BDD (Playwright, red-first) under the Mandatory Problem-Solving
Loop.

## Problem-Solving Loop record

1. **Expected:** with the dialog open and the record unchanged, a
   refresh cycle repaints nothing — no rebuild, no linked-row
   refetches, no flicker; an active editor is never destroyed by any
   refresh.
2. **Problem:** owner video (message 2969): on a real epic with 17
   linked tickets the Linkage section visibly re-read every cycle with
   nothing changing, and starting an edit could be "cut out" by a
   refresh that replaced the whole dialog.
3. **Root cause:** `maybeRefreshDialog` called `reloadCard()`
   unconditionally — every 5s cycle re-rendered the entire dialog, so
   every linked ref refetched and every section repainted through its
   placeholder state; and the `dialogEditingActive()` guard ran only
   before the fetch, so a response already in flight when an editor
   opened still landed and replaced the DOM.
4. **Reproduction:** Playwright mobile pass — count `/record` reads
   across a quiet 7s window (pre-fix: 4 — the reload plus three linked
   lookups) and tag a section node (pre-fix: replaced); for the race, a
   600ms-delayed changed response with the editor opened mid-flight
   (pre-fix: editor gone).
5. **Pre-fix comparison:** guard run failed exactly as predicted:
   "4 record reads in one quiet cycle".
6. **Fix:** the refresh cycle fetches the record itself, re-checks
   `dialogEditingActive()` after the response arrives, compares the
   payload against `lastDialogRecordJson` (set by every render), and
   returns without touching the DOM when identical. `reloadCard()`
   remains the force path for user actions, so cancel/save behavior is
   unchanged.
7. **Re-run:** all three scenarios green ×3.
8. **Guard:** the quiet-cycle fetch budget, the DOM-stability tag, and
   the delayed-response editor race are permanent in the mobile pass;
   t/19 pins the snapshot variable, the identical-skip comparison, and
   the post-fetch guard re-check.

# DD-444

## Title

Mutations that bypass the project lock.

## Source

Found by me while building DD-443, raised rather than fixed there, and
recommended to the owner as the thing to do next.

## The defect

`SKILLS.md` states that every mutation takes the project lock. Ten
methods do not: comments, checklists, gates, evidence and attachment
references all read the record, change it in memory, and write it back
through `_replace_record` with nothing held.

That is a read-modify-write with no exclusion. Two comments added at
the same moment both read the record with two comments, both append
their own, and both write three — so one comment is silently lost. The
same is true of every checklist item, gate, evidence entry and
attachment reference. Nothing errors and nothing is logged; the work
just is not there.

Documentation and behaviour disagreed, which is the part that makes it
worth fixing rather than describing. An agent that has been told
mutations are serialised will not defend itself against this.

## Why it was not simply wrapped before

`_with_project_lock` opens its own handle and takes `flock` on it. Two
handles on the same file from one process are two independent lock
entries, so a locked operation calling another locked operation
deadlocks against itself — which is why these methods were left
outside rather than wrapped.

## Fix

Make the lock reentrant. The wrapper records which project roots it is
already holding; a nested call for a root already held runs its code
inside the lock that is already ours instead of taking a second one.
Journal depth is already tracked this way, so the two now agree.

With that, each of the ten methods wraps its whole read-modify-write —
not just the write — because the read is half the race.

## Acceptance criteria

1. A locked operation can take the lock again for the same project
   without deadlocking, and still holds it throughout.
2. A nested call for a *different* project takes that project's own
   lock.
3. Every one of the ten methods holds the lock while it reads and
   writes.
4. A failure inside a nested operation still discards the journal and
   releases the lock.
5. The documented guarantee in `SKILLS.md` is now true.

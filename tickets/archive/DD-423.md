# DD-423

## Title

Optimistic concurrency for same-field dialog edits.

## Method

Engine TDD + provider/HTTP ATDD + Browser BDD (Playwright), red-first.

## Problem

Owner discussion (voice messages 2927/2928) and approval ("Do it",
message 2932): two users editing the same card from different machines.
Different-field edits already merge safely — each save is a single-field
read-modify-write under the project lock — but two edits to the *same*
field silently last-write-win, discarding the first save without warning.

## Design

- `record_update` accepts `expect => { field => base }`: inside the
  project lock, before any change is applied, each expected base is
  compared against the stored field (`_matches_base`: null only matches
  unset; values compare as strings); a mismatch dies
  `Conflict: <field> changed while you were editing` and writes nothing.
- The browser `update` provider passes an optional scalar `base` from the
  payload through as `expect` for the saved field; structured bases are
  refused.
- The `_mutation` wrapper flags `Conflict:` errors with `conflict: true`
  in the 422 JSON so the dialog can distinguish recovery from plain
  validation failures.
- Each dialog field editor captures the value it opened with and sends it
  as `base`; on a conflict response the dialog shows the explanation and
  reloads the fresh card instead of silently overwriting.
- Lists and comments keep their existing semantics (out of scope; the
  same `expect` engine hook can host them later if wanted).

## Acceptance

- engine: stale base rejected with the conflict error and no write;
  matching base applies; null base matches only an unset field; numeric
  bases compare by value
- provider: `base` round-trips into `expect`; structured bases refused;
  a conflicted save leaves the record untouched
- HTTP: a conflicting `/update` returns 422 with `ok:false`,
  `conflict:true`, and the explanation; ordinary failures carry no
  conflict flag; `base` travels through the route
- dialog: saves carry the editor's opening value; a conflict shows
  "changed while you were editing", reloads the card, and the message
  stays visible after the reload
- Docker tests pass; coverage `100.0%` statement and subroutine; taint
  and primitive-scan gates pass; `cover_db` cleaned
- Playwright proves the base in the update payload and the full conflict
  recovery (error shown, editor closed, record re-read) ×3
- `README.md`, `docs/foundation.md`, `Changes`, `VERSION 0.34`, tickets,
  commit, and push complete from the `tira` repository
